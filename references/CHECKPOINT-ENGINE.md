# 测试点结构化分析引擎（Checkpoint Engine）

> 来源：Lemon Checkpoints 方法论，已合并为本 Skill 的内置分析引擎。
> 定位：它不替代主流程的 XMind 用例生成，而是在用例生成之前/之外，把"需求里明确写的"和"我猜的"彻底分开，输出可直接用于评审的结构化检查点交付物。

## 1. 目标

将需求材料转化为结构化测试检查点清单，把"需求已有依据的事实"和"尚未确认的规则"分开，输出可直接用于评审的交付物。

## 2. 核心原则

| 原则 | 要求 |
|------|------|
| **事实与猜测分离** | 每条测试点必须标注证据来源：需求依据 / 经验假设 / 待确认 |
| **按用户目标链路排序** | 先按用户完成目标的业务链路排风险，再拆批次；不按接口、字段等技术维度拆表 |
| **标准覆盖方向查漏** | 使用 C01-C14 覆盖方向矩阵逐项查漏，输出覆盖地图暴露盲区 |
| **不自行拍板** | 材料没写的规则不得自行决定，一律单独列入待确认表 |

## 3. 证据标注规则

| 标注 | 判定条件 | 处理方式 |
|------|---------|---------|
| **需求依据** | 需求材料中有显式描述（含备注、公式、口径说明） | 测试点证据依据字段注明章节来源，如 `需求依据 §用户端-情况二 备注` |
| **经验假设** | 材料未写，但来自行业/历史项目的通用经验 | 测试点保留并标注 `经验假设`，注明经验来源，评审时复核确认 |
| **待确认** | 材料未写，且该规则直接影响预期结果结论 | 测试点可保留但预期结果标注 `[待确认]`，同时进入待确认表；禁止把待确认规则写成已确认结论 |

## 4. 用户目标链路与批次划分

**链路提取**：按"用户进入入口 → 关键操作 → 完成目标"梳理业务链路，每条链路先问"哪一步断了用户就走不下去"，再排测试点顺序。

| 批次 | 定义 | 评审用途 |
|------|------|---------|
| **A 冒烟** | 主链路阻断点，通了才能继续测 | TL 直翻 A 批次即见 S0 路径 |
| **B 重点** | 核心业务规则、计算公式、数据范围与口径 | 评审主战场 |
| **C 扩展** | 边界、异常、UI、联动、性能等非主链路场景 | 全量回归依据 |

## 5. 测试点五字段

| 字段 | 定义 | 子要素 |
|------|------|--------|
| **触发情况** | 什么条件下触发这个测试点 | 前置状态判定、业务触发条件、异常触发场景 |
| **样本数据** | 用什么样的数据来验证 | 典型正向数据、边界值样例、异常构造数据集 |
| **核对结果** | 什么算通过、什么算失败 | 通过判定标准、失败现象特征、预期输出对比 |
| **失败影响** | 这条挂了影响面有多大 | 核心业务阻断、功能降级范围、风险严重等级 |
| **证据依据** | 判断依据来自哪里 | 需求依据标注、经验假设标注、待确认对齐项 |

## 6. 标准覆盖方向 C01-C14

| 编号 | 方向 | 子方向 |
|------|------|--------|
| C01 | 正常流 | 主路径闭环、预期返回校验 |
| C02 | 异常流 | 参数校验拦截、容错降级机制 |
| C03 | 边界值 | 空值与极值、溢出与阈值 |
| C04 | 权限 | 越权访问控制、角色身份鉴权 |
| C05 | 并发 | 高并发争抢、重复触发去重 |
| C06 | 重试与补偿 | 幂等性保障、失败补偿与退避 |
| C07 | 审计与埋点 | 操作日志留存、埋点数据完整 |
| C08 | 会话与状态恢复 | 页签/模式切换状态保留、状态一致性重建 |
| C09 | 数据一致性 | 跨页同口径、最终一致性、事务回滚校验 |
| C10 | 上下游依赖 | 接口契约适配、第三方超时熔断、算法/智能体数据源 |
| C11 | UI 展示 | 列名/顺序/单位/排序/样式/文案 |
| C12 | 联动刷新 | 筛选/日期/页签切换联动、分页回首页 |
| C13 | 性能容量 | 大数据量响应、批量操作带入 |
| C14 | 定时任务 | 定时触发时点、失败重发与补偿 |

> 覆盖地图以"方向 × 链路"矩阵呈现：已覆盖打 ✓，空白方向必须注明"可接受风险"或补测试点，不允许静默留空。

## 7. 工作流（嵌入主流程）

```
第1步 需求解析        → Phase 2 步骤 1-8（模块/链路/显性规则/隐含约束[待确认]）
第2步 测试点生成      → Phase 2 步骤 9：五字段 + 证据标注
第3步 批次划分        → Phase 2 步骤 10：A 冒烟 / B 重点 / C 扩展
第4步 覆盖方向查漏    → Phase 2 步骤 11：C01-C14 覆盖地图
第5步 五表输出        → Phase 3 步骤 5：test-docs/checkpoints_<时间戳>.md
```

## 8. 五表交付物

| 交付物 | 内容 |
|--------|------|
| **执行看板** | 批次 × 链路数量矩阵 + 各链路冒烟路径一句话概述 |
| **测试清单** | 编号 / 批次 / 链路环节 / 五字段（触发情况、样本数据、核对结果、失败影响、证据依据） |
| **待确认表** | 编号 / 问题 / 材料出处 / 影响范围 / 建议确认人 |
| **规则证据表** | 规则编号 / 规则内容 / 材料出处（只收材料显式写明的事实） |
| **覆盖地图** | C01-C14 × 链路矩阵 + 空白方向风险说明 |

## 9. 约束

- 不编写逐步测试操作说明，不替代完整测试计划（逐步用例仍由主流程 Phase 3 的 XMind 管道承担）
- 材料没写的规则不得自行拍板，待确认规则必须单独列出
- 待确认规则不得以已确认结论的形式出现在测试清单的预期结果中
- 测试清单编号可与需求ID互相关联，复用主流程追溯矩阵
