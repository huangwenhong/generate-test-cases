## 1. 目标与验收

### 1.1 已确认的规则及资料覆盖关系

1. 包含历史订单导入、模板下载、导入记录、错误报告、订单分页筛选和批量删除。历史订单不经过订单中心，不触发支付、生产、库存或物流流程。
2. 单文件不设业务行数上限，空白行不计数。原始行写入暂存表和后续订单处理均每批最多 500 条。仍校验文件大小、格式、表头、完整性及是否有数据。
3. 使用当前模板15列，不增加长宽高、压线方式、重压方式。按产品最新确认，历史订单列表不返回压线方式、纵压，不预留空值字段，也不增加导入列或数据库字段；列表不返回 branchNumber、salesmanName、canDelete，原支数及业务员的内部存储规则不变，删除权限仍由删除接口校验。单位改由后端调用`POST /record/getShowUnitmm`取得，显式传真实供应商ID；按2026-11-26用户确认，showUnitmm=true→mm、false→cm。导入接口移除sizeUnit请求字段，覆盖此前前端选择单位的约定。
4. 下单时间为空时取任务创建时间（北京时间），全文件统一；单价、面积、金额为空按 0，不推导或校正它们之间的关系。
5. 默认建立客户档案和按需调用产品服务上架，没有“是否建档”开关。客户先本地建档，再强制注册易网，不受 `syncRegister` 配置影响。
6. 联合销售主体导入时，联合和真实销售主体的客户都必须存在并关联；订单只存一份，`skey=真实公司 ID`，`customer_info_id=联合客户本地主键`。普通供应商及非销售主体成员关联自己的客户。
7. 文件完整暂存后、业务处理前按真实供应商 ID 调用 `POST /third/erpQueryOnSaleProduct` 查询全部已上架产品。匹配到已有产品直接复用，仅未匹配且本任务尚未处理的产品调用批量上架。查询命中或逐项返回 PRODUCT_EXISTS 时产品新增数不增加；PRODUCT_EXISTS 继续兜底查询后的并发新增。本地不建产品档案表。
8. 同一真实公司下，同一个 Excel 文件地址不允许再次创建导入任务，包括首次任务失败的情况。重新上传得到新地址可导入，不按文件内容或订单字段去重。
9. 订单号为 `YDLH + yyyyMMdd + 随机数字`，日期取生成日期，不取历史下单日期；以数据库全局唯一索引兜底。
10. 导入任务记录本地导入及报告结果。大数据定时扫描 crm_history_order 表，同步已提交的新增订单和逻辑删除变更。
11. 仅保留 getImportTaskList.do 导入记录分页接口，不提供单独的详情接口。按最新 UI 返回操作人、操作时间、导入成功/失败数、客户/产品新增数、报告可用信息及导入进度；仅当前页本地终结且有成功订单的任务按 ID 查询大数据已统计条数，以 syncedCount/successCount 展示。
12. 批量删除在本地标记订单为逻辑删除，保留客户、产品及原导入记录。大数据后续扫描处理删除变化。
13. 大数据负责定时扫描、统计更新及按任务统计进度。本服务提供订单表和只读进度查询契约。
14. 导入暂存表按 Excel 模板 15 列逐列存储，另存源行号、行状态和失败原因。整个文件完全暂存后才开始业务处理。已启动的导入中断后只收尾和恢复报告。
15. 导入和删除写入流程不调用大数据接口。同步有扫描延迟，进度查询失败时仍返回本地导入结果。
16. getImportTaskList.do 只返回当前真实公司内当前用户创建的导入记录，只向大数据查询本次授权分页结果中的任务。
17. 本次订单模块接口统一使用 /order/v2 前缀。
18. 历史订单导入权限覆盖提交导入以及导入中的客户建档和产品上架。合格数据由导入任务自动调用产品服务，不设置导入或产品上架 Apollo 开关，也不单独授予上架权限。
19. 按本次用户确认保留 `file_key` 及文件地址防重规则。提交接口增加 Redis 分布式锁，按真实供应商隔离；同一真实供应商同时最多存在一个 `QUEUED/RUNNING` 导入任务，不区分提交用户和文件地址。已有任务未结束时拒绝新建，不另建任务排队；不同供应商可并行。报告生成及大数据同步不占用导入名额。

## 3. 接口与权限

完整字段见 [api.md](api.md)。共 6 个本服务接口，统一以 `/DJEASYORDER/order/v2/` 为前缀，POST JSON，下载成功返回文件流。Controller 类级映射为 `order/v2`，`/DJEASYORDER` 为应用上下文。


| 方法 | 相对路径                          | 用途                                     |
| ---- | --------------------------------- | ---------------------------------------- |
| POST | `importHistoryOrder.do`           | `fileUrl`，后端查询供应商单位后提交异步导入 |
| POST | `downloadHistoryOrderTemplate.do` | 系统变量读取模板并下载                   |
| POST | `getHistoryOrderList.do`          | 历史订单分页和筛选                       |
| POST | `getImportTaskList.do` | 导入记录分页，返回本地操作结果、报告信息及当前页逐条大数据进度 |
| POST | `downloadErrorReport.do`          | 按任务 ID 下载失败行报告                 |
| POST | `deleteHistoryOrder.do` | 批量逻辑删除历史订单 |

- 登录接口的身份从可信 `userUtil.getUserInfo()` 取得：`realCompanyId` 为任务及订单 skey；`ucompany` 为业务客户侧公司。Controller 不调用 `setBaseBo`。
- 导入入口校验有效登录、历史订单导入权限及文件归属。该权限覆盖任务内的客户建档和产品上架。建档仍执行现有业务校验。列表、记录、下载和删除按各自功能校验读、导入或删除权限，后端按现有菜单授权体系执行。

## 4. 服务逻辑、事务与失败处理

### 4.1 文件受理、流式暂存和分批处理

1. 请求线程验证身份、导入权限、文件归属和扩展名。创建任务前调用单位接口，显式传operator.getRealCompanyId()，联合销售主体也传真实供应商。返回success=true、data存在且showUnitmm非null才解析：true→mm、false→cm；使用Boolean接收，不能将缺失值当false。失败、超时或空值返回UNIT_QUERY_FAILED，不建任务、不建档，修复后可用同一文件地址重试。成功查询一次后把size_unit随任务一并保存，所有批次及订单复用该快照；QUEUED 重投和报告重建使用已保存的单位。生成任务UUID，缺省下单时间采用任务create_time。
2. 规范相对路径按UTF-8计算SHA-256，由后端生成 `file_key`，数据库UNIQUE(skey,file_key)防同地址重复。保留路径大小写和对象名，不按内容去重；同地址即使供应商配置的单位后来变更仍重复。摘要相同须核对完整地址。随后按可信 `realCompanyId` 获取供应商级 Redis 提交锁，拿不到锁返回 `IMPORT_BUSY`，Redis 异常返回 `IMPORT_LOCK_UNAVAILABLE`，均不新建任务。
3. 在提交锁内开启独立短事务，按 `skey` 查询是否存在 `local_status IN ('QUEUED','RUNNING')` 的任务，不加个人创建人过滤。存在则返回 `IMPORT_BUSY`；不存在时检查同地址记录，再插入 `local_status=QUEUED` 的任务。事务提交完成后由请求线程释放锁，再投递专用线程池。释放锁不释放导入名额，后续请求仍受数据库活动状态约束。池拒绝时保留QUEUED且继续占用名额，扫描器可重新投递该任务；提交后进程崩溃、尚未投递也按同样方式恢复。
4. 流式下载文件并检查真实大小。Excel 只读取一次，只读“订单表”，忽略说明 Sheet。检查格式、固定表头、文件是否完整和是否有非空数据行。原始 15 列各写一个暂存字段，以可复核的文本保存。合法 Excel 日期单元格转换为可还原的日期文本，文本单元格保留原始内容，手机号不通过浮点转换，空单元格存 NULL。业务格式错误也写入，不提前填默认值或截断。空白行跳过，其他行按 `task_id + source_row_no` 每批最多 500 条存为 `PENDING`。整份文件读完且所有暂存批次提交后写入 `total_count`，作为允许开始业务处理的标记。不设业务行数上限。暂存中断或文件级校验失败时终结为 `FAILED`，`total_count` 仍为空，已暂存的部分行仅供清理，不建档、不上架、不落单、不生成逐行报告。
5. 完整暂存后、客户及产品等业务处理前，按真实供应商查询一次全部已上架产品，校验响应并建立只保留匹配所需字段的只读索引。查询失败或结果无法可靠匹配时任务终结为 FAILED，不创建客户、产品或订单，不能视为空集合。随后按 `task_id + row_status=PENDING + source_row_no` 从暂存表依次取每批最多 500 条。逐行校验并批量查询客户，再执行客户注册、地址及按需产品上架；已上架产品直接复用。业务校验通过的行才进入相关业务步骤。整个任务沿用单执行者保护，批内按原始行序处理，不用 `OFFSET` 翻页。
6. 批内用 Map 去重。跨批次从暂存表按本批手机号、产品键批量读取此前结果；产品先复用历史结果，再匹配已上架产品索引，仍未匹配才调用上架。每个键的首次处理结果只写在该键的代表行上，保留必要的 ID、名称或脱敏失败原因，区分已有产品复用与新增成功。基础校验通过的首条行负责首次建档，后续行复用该客户的结果，收货地址仍按当前行处理。产品结果未知或已确认成功时不重复发起上架。不在内存里维护随文件增长的全任务字典；已上架产品索引只随供应商产品数增长，任务结束释放，容量需压测。
7. 一个短事务写入本批成功订单，将对应暂存行改为 `SUCCESS`，其余已确定失败的行改为 `FAILED` 并保存原因，同时提交订单成功数。订单写入事务回滚时，相关行仍为 `PENDING`，不留下成功状态。新建客户计数与本地建档同事务提交，产品新增数仅按本任务首次确认新增的产品键统计。
8. 正常处理完后本地 `SUCCESS/PARTIAL/FAILED`。任务中断时确认执行者已停止，按已提交订单校准成功数，任务标记 `FAILED`，保留已提交的行状态及原因。`PENDING` 表示尚未提交最终处理结果，可能已有客户或产品副作用。文件完整暂存且 `total_count > success_count` 时，终结事务同时把 `report_status` 置为 `BUILDING`。每批已提交订单均纳入大数据后续扫描范围。报告独立生成。
9. 文件完整暂存且本地任务终结后，按源行号分批导出 `FAILED` 和 `PENDING` 行。保留原始 15 列，追加“错误原因”。`FAILED` 输出已持久化的原因，`PENDING` 标注“任务中断，未提交最终处理结果”，`SUCCESS` 始终排除。EasyExcel 流式生成并上传，上传成功后设为 `READY`。上传失败时优先重传已有报告，临时文件丢失时复用任务扫描和执行锁从暂存表重建，报告恢复只读暂存数据，不依赖源 Excel，也不执行导入业务。
10. 源文件暂存完成后清理临时文件，已上传报告及时清理。原始行含手机号和地址，只用于导入、排查和报告，保留期上线前确认。仅对本地已终结且超过保留期的任务分批清理暂存数据，与报告生成共用任务执行锁。保留任务记录、防重键及已提交订单。暂存数据清理后仅能下载仍在文件服务中的报告。

专用线程池建议核心/最大2、队列10、AbortPolicy。任务表存任务状态和汇总，暂存表存逐行结果。已启动任务中断后不自动续跑。用户结合报告核对未成功行和外部处理结果后，可用模板整理这些行并重新上传为新地址。

### 4.3 客户与产品建档

- 手机号归并在当前任务、当前真实公司范围内进行；基础校验通过的首条行作为新客户名称/基础地址/业务员来源。错误行不作为首条建档依据。不同名称的后续订单关联同一客户，仍保留各自 Excel 名称快照。
- 已有客户复用，不覆盖名称、基础地址、已有负责人；新增收货地址按规范地址和收货人去重追加。已有客户仍校验/补齐易网注册信息，不能因“已有”跳过强制注册要求。
- 地址处理建议：调用现有 Amap 能力取得经纬度及可解析行政区划；地址无法定位或必要市区信息缺失时，依赖该地址的行失败。没有街道编码时可保留空值，不编造 code。已有客户不需要用新地址覆盖基础地址。此为对已认可建档失败策略的具体落地，联调时覆盖该边界。
- 普通公司 D：建/取 `skey=D` 的本地客户 cd。联合销售主体 A（业务公司 U）：先在本地短事务内建/取 cu(skey=U)、ca(skey=A)，设置 `ca.union_customer_id=cu.id`；两侧任一失败则该次本地事务回滚，不能落单边成功订单。非主体成员 B 仅按 B 当前客户处理，不复制到销售主体。
- 本地建档完成并提交后，再调用 `OutUserService.register`；返回 success/repeat 且 customerId 有效才继续。按现有语义写回 cu/ca 的易网客户 ID，订单同时保存本地客户 ID 和易网客户 ID，接口分别统一命名为 `infoId`、`customerId`，对应数据库 `customer_info_id`、`ynet_customer_id`；两种 ID 不混用。
- 登记和外部地址调用均不放入长事务；注册、地址或产品失败时保留此前成功的档案，相关订单失败，其余继续。新客户计数按去重手机号计，一组联合/真实客户记 1 家，不记 2 家；补齐缺失一侧也记 1 家。计数与本地创建事务一并提交，跨批次复用暂存表中的处理结果，中断不重新建档续跑。
- 本次新建/复用客户必须在短事务中重新查询，沿用客户现有手机号锁并核对其多实例互斥语义；不得用请求防重复点击保证客户唯一。先核对现网客户索引，不在本方案盲加历史表唯一约束。
- 业务员按业务公司/真实公司分别解析可授权身份，不把联合员工 ID 直接塞给真实公司的负责人字段。已有负责人不覆盖；解析冲突返回建档失败。
- 产品按真实供应商+材料代码+层数+规范楞型匹配，供应商传 A/B/D，绝不传 U。先调用 `POST /third/erpQueryOnSaleProduct`，入参只有 supplierId，返回该供应商全部已上架产品。查询命中后直接复用产品 ID 和名称，保存代表行结果，不调用上架，也不累计新增数；仅未命中且本任务尚未处理的产品调用 `POST /third/erpBatchAddProduct.do`。新查询返回数字 flutetype，上架请求使用字母楞型，应复用 ProductFeign 字典及 LayerModel/EdgeModel 转换；数字编码与 edgeId 的关系待联调核对，不硬编码。查询失败、超时、data=null、跨供应商或无法可靠匹配等情况终结任务为 FAILED，不降级为全部新增。成功返回 [] 才表示无已上架产品。
- 新增请求没有 productName，名称以产品服务返回为准，用户示例为 MAT100/B；此前建议“材料名称-层数楞型”不能直接通过该接口指定。仅新增产品时默认传 productType=customized，已上架产品不因类型或渠道不同而自动再次上架；无需模板加列或前端传入。材料名称是否为材料代码及不同层数的产品名称区分仍待确认。本地不建产品档案表，productId 仅用于产品结果确认/任务内缓存。
- 过滤已上架及任务内已处理产品后，按实际新增请求重新生成从 1 开始的 index，逐项匹配产品和依赖行，不沿用过滤前序号。新增成功时正常落单并计产品新增数。PRODUCT_EXISTS 表示查询后仍可能出现的并发重复，按复用继续，不写入错误报告，也不增加产品新增数。该分支允许缺少 productId。返回已有名称时保存，未返回则 product_name 为空，材料名称仍按 Excel 展示。详见 [产品接口契约](api.md#71-产品批量上架)。
- 其他逐项错误使用实际错误码及脱敏原因，超时或响应缺失时标明结果不明，不自动重发整批。

### 4.4 订单号、事务及恢复

- 订单号格式建议固定 `YDLH + yyyyMMdd + 18 位随机十进制数字`，总长 30；使用 Java 8 SecureRandom，保留随机部分前导 0。本表 `UNIQUE(order_no)` 是保证，不以随机碰撞概率代替唯一约束。
- 批次插入若订单号唯一键冲突，回滚该批，重新生成冲突订单号后有限重试（建议最多 5 次）；次数耗尽则该批逐行定位并报告，不能对订单号冲突使用 INSERT IGNORE 丢行。仅重试明确的该唯一键冲突，其他 SQL 异常不得当作随机碰撞吞掉。
- 行订单 ID 在最终写入前生成，业务主键为 UUID；rowid 为数据库 BIGINT 自增，用于内部排序和增量扫描，允许空洞和任务间交错。
- 一个事务只覆盖一批本地写入，使用独立 Spring Service 的代理方法，禁止依赖自调用开启新事务。单批失败回滚不影响此前批；外部已创建档案不尝试分布式回滚。
- 异步捕获用户身份快照，不保存 token，不在任务表持久化业务公司 ID。进线程先 setLocalUser，操作两侧公司时使用独立快照并 finally 恢复，整个任务 finally removeLocalUser，不能修改请求线程共用 UserModel。QUEUED 重投时按任务 operator_id 获取可信用户信息并按现有联合身份逻辑初始化上下文，校验 realCompanyId 与任务 skey 一致；无法取得可信身份或公司不匹配时终结为 FAILED，记录任务级原因，不猜测业务公司或执行建档。
- 扫描器仅自动重新投递QUEUED任务；已RUNNING任务不自动重导。每次执行通过任务ID命名的GET_LOCK专用连接互斥，锁全程持有，finally释放；本地写事务先锁任务并校验worker_epoch，拦截失锁旧执行者继续写入。发现RUNNING时可零等待尝试同一锁：锁仍占用则跳过；锁已释放后再次核对状态，仍RUNNING则仅做中断收尾，递增epoch、标记FAILED、校准成功订单数量并恢复报告处理，不继续读取执行订单。若数据库代理不支持会话锁，需接入已有可信互斥能力。
- 中断前已提交的订单和档案保留；未提交批次回滚。客户/产品新增数仅表示已持久确认的创建结果；极端情况下外部已成功但确认尚未落库，新增数可能少于外部实际创建数，任务须显示中断错误并提示核对，不承诺通过断点恢复补全该数。数据库死锁可有限重试未提交事务，未知结果的外部调用不能盲目重放。
- 供应商提交锁使用 `djeasyorder:history-order:submit:{realCompanyId}`，供应商 ID 只能取可信上下文；不同用户、不同文件及联合销售主体的同一真实供应商必须命中同一锁。复用 `RedissonService.lock(key,0,-1)`，不等待竞争锁，并使用 Redisson 自动续期；实施时核对有效版本支持该语义。本地缓存的 Redisson 3.10.1 源码已确认 leaseTime=-1 走续期逻辑。Redis 异常不降级为无锁提交。
- 提交锁仅包围“查询活动任务、文件防重、创建任务及事务提交”，单位接口、文件读取和异步导入均在锁外；数据库查询必须走主库且在获锁后新建事务，避免读到旧快照。通过独立 Spring Service 代理完成短事务，外层请求线程在事务方法返回后于 finally 解锁；只释放本线程持有的锁，不跨线程交接。锁丢失时不得继续创建任务。事务已提交后的解锁异常不能回滚受理结果或另建任务，应记录并告警排查。
- `QUEUED/RUNNING` 表示供应商仍被当前任务占用；仅本地终结为 `SUCCESS/PARTIAL/FAILED` 后允许下一个任务。扫描器只重投既有任务，不新建同供应商任务；RUNNING 中断须按前述执行锁确认旧执行者已停止后收尾，不能只按超时把任务改为终态。报告恢复和暂存清理仍使用任务级执行锁，与供应商提交锁职责不同，不因报告重建重新占用导入名额。

### 4.5 大数据定时扫描与导入记录进度

1. 大数据定时读取已提交的 `crm_history_order`，以 `id` 区分订单、`task_id` 统计导入进度、`skey` 区分真实供应商。新增订单和 `isdel=1` 的变更均要扫描。若按更新时间增量扫描，`(update_time,rowid)` 可用于分页，并需覆盖同时间戳、提交乱序和重试，避免漏单。大数据按订单 ID 幂等更新或移除统计，具体扫描策略和延迟由大数据确认。
2. `getImportTaskList.do` 先按可信真实公司及创建人完成本地分页和总数查询，只为当前页本地已终结且 `successCount>0` 的任务，在本地事务外逐条调用 `/ybill/import_order/statistics_progress`。每次以本地查到的任务 ID 作为唯一业务入参 `task_id`，不接收任意任务 ID、不读取页外或其他用户任务。返回 `success=true`、`code="10001200"` 且 data 中有唯一有效结果时，取 `data[0].statistics_order_cnt` 映射为该列表项的 `syncedCount`。详见 [大数据进度接口](api.md#72-查询导入同步进度)。
3. UI 的操作结果由总数、成功数、失败数及客户/产品新增数展示，报告由状态及下载标志控制；导入进度用 `syncedCount / successCount` 展示。仍在本地导入时 syncedCount 为 null，按 localStatus 展示排队或导入中。已终结但无成功订单时返回 0，不查大数据，显示无需同步，不计算 0/0。超时、失败、字段缺失或计数越界仅令该条 syncedCount=null，其他字段、任务及分页照常返回，不改写导入错误原因；正常返回 0 与查询失败须区分。
4. 当前大数据接口只支持单个 task_id，本次不要求新增批量接口。仅对当前页符合条件的任务各查一次，使用单次短超时及整页总耗时预算（建议 3 秒，联调校准），单次超时不超过剩余预算；预算耗尽时未查询项返回 null，不自动重试、不新增缓存或无界线程池。前端只刷新打开弹窗的当前页，关闭即停止；当前页任务均本地终结、报告不在生成且进度完成或无需同步后可停止自动刷新。
5. `statistics_order_cnt` 是已统计订单数，包含已取消的订单，即逻辑删除记录。原导入成功数也不因删除下降。该进度用于衡量导入数据的统计覆盖，删除变更是否已应用仍由大数据扫描核实。即使导入后续批失败，已提交订单仍纳入扫描。联调覆盖先统计后删除与首次扫描前删除两种场景。

### 4.6 批量逻辑删除

- 单次提交 1～500 个订单业务 ID，先去重。事务内按真实公司查询并锁定目标订单，核对全部存在且来源导入任务已本地终结。越权、缺失或源任务仍在运行时整体拒绝。
- 仅对 `isdel=0` 的订单更新 `isdel=1`、删除操作人和删除时间，并更新订单 `update_time`。同公司已删除的目标视为已完成，保留原删除记录。接口返回本次实际更新的条数。
- 订单列表本地立即隐藏已删除记录，保留客户、产品和原导入记录。大数据后续扫描处理逻辑删除，删除接口只确认本地提交结果。

### 5.1 导入任务与暂存数据

- 任务表 `file_url`、`file_key` 和 `size_unit` 为必填。按本次确认移除业务公司 ID 字段，业务客户侧公司从可信执行上下文取得；`skey` 仍保存真实公司 ID。`worker_epoch` 仍负责本地导入执行保护。
- `file_key` 是规范化文件相对地址的 SHA-256 十六进制摘要，非文件内容摘要。使用固定 64 字符的摘要与 `skey` 建联合唯一索引，避免直接以最长 1024 字符的 utf8mb4 地址建完整唯一索引时受索引长度限制。摘要相同须核对完整地址。删除该字段必须提供等效的数据库并发防重约束；仅先查同地址再插入不能保证 SC-007，同内容重新上传到新地址仍允许导入。
- `local_status`：`QUEUED` 为排队待执行；`RUNNING` 包含文件暂存和业务处理；正常处理结束时，全部行成功为 `SUCCESS`，部分行成功为 `PARTIAL`，全部行失败为 `FAILED`；文件级校验失败或任务异常中断也为 `FAILED`，中断时可能已有成功订单。状态只反映本地导入，不代表大数据同步或报告结果。
- `report_status`：`NONE` 为尚未满足报告生成条件或无需报告；完整暂存、本地终结且存在未成功行时置为 `BUILDING`，涵盖生成、上传及恢复重建；上传完成且有可信报告地址时为 `READY`；生成或上传失败为 `FAILED`。开始恢复时重新置为 `BUILDING`。全部成功或文件未完整暂存时无需逐行报告。报告失败不覆盖 `local_status`。
- `error_message` 保存脱敏的文件级或导入任务级失败原因，供导入记录列表展示，例如表头不符、文件无法读取、任务异常中断；无此类错误为 NULL。每行的校验、客户或产品处理错误保存在暂存表 `failure_reason` 并导出报告，不将所有行错误拼入该字段。报告生成失败由 `report_status` 表达，大数据进度失败由对应列表项的 `syncedCount=null` 表达，均不覆盖已有导入失败原因。
- 成功订单由 `task_id` 关联导入任务。任务表保存本地导入结果及报告状态。列表查询得到的逐条 `syncedCount` 仅作为返回字段。文件名、单位及 processedCount 不作为本次导入记录返回字段，任务表原有文件地址和单位快照继续用于导入处理。
- 暂存表每个模板字段对应一个 `raw_` 列，映射和顺序见 DDL。报告从逐列原始值及失败原因按批生成。

### 5.2 查询与配置

基础 DAO 与 Mapper 一表一套，沿用 order 包，建议新增 `order/dao/HistoryOrderDao.java` 等及 `order/dao/mybatis/mapper/HistoryOrderMapper.xml`。批量上限 500，空集合立即返回，所有值用 `#{}`，分页显式列、稳定排序，优先批量组装不用 N+1。

- 导入任务列表使用 `(skey,operator_id,create_time,rowid)`。列表和总数先按真实公司及创建人过滤，报告再按任务 ID 校验归属，进度仅按已授权的当前页任务 ID 查询。提交时的活动任务检查另用 `(skey,local_status)` 索引，只限制真实供应商，不套个人过滤；该普通索引不代替供应商 Redis 提交锁。
- 订单列表 `skey + isdel + order_time + rowid`；日期查询采用 `[开始日00:00:00,结束日次日00:00:00)`；未选日期仍数据库分页，不全量读取。
- 名称/手机号/材料 contains 模糊匹配；转义 `%/_/反斜杠` 按普通文本查询。此类前导通配无法依靠普通索引加速，按公司和其他条件缩小范围，在十万/几十万级数据上 EXPLAIN 和压测，不盲加无效索引。
- 暂存表主键为 `(task_id, source_row_no)`，按 `(task_id, row_status, source_row_no)` 查询待处理行。每个客户键和产品键只在结果首次确认的代表行保存，使用两个可空唯一索引支持按本批自然键查历史结果。产品键由规范化后的真实供应商、材质代码、层数、楞型确定。缓存字段只存必要结果，不复制原始行。处理结果随对应批次提交。
- 报告按暂存表主键顺序读取，每批最多 500 行。订单逻辑删除不会改写历史导入行状态，也不会让原成功行进入报告。
- taskId 和 orderId 使用 UUID 字符串，金额等在 API 中使用十进制字符串。
- 订单表增加 `(update_time,rowid)` 扫描索引，供大数据结合实际扫描条件验证。关联客户 ID 长度在实施前核对实际 DDL。
- 暂存原始行和失败原因仅用于本任务及授权报告，不对外提供逐行查询接口。日志不打印手机号、地址、完整 Excel、token 或带签名 URL。

## 6. 技术选择与影响

1. 新订单模块使用/order/v2入口及独立历史订单表；旧crm_order与旧模块代码不作为本次新能力入口。本次历史订单不经过订单中心，大数据对接后决定纳入报表的方式。
2. Excel 流式读取一次，暂存和处理均每批最多 500 行，业务不限制行数。暂存增加一份原始行及处理结果的数据库存储，保留期内可恢复报告。单批业务内存有界，EasyExcel 底层共享字符串及上传下载仍需实测峰值。文件格式容量和文件大小限制仍适用。
3. 大数据以订单表为增量来源，导入记录分页为当前页符合条件的任务按 ID 查询对方已统计条数。只保留分页接口，前端无需按行再请求详情。现有外部接口仅支持单任务，整页设耗时预算，避免串行超时叠加；不新增批量外部契约、缓存或后台进度任务。删除变更同样通过订单表传递，导入任务仅维护本地结果。
4. 所有事务、监听器、Feign、时间和随机 API 沿用 Java 8、javax 与现有 Boot/MyBatis。
5. 保留 `file_key` 唯一索引解决同地址长期防重，新增供应商级 Redis 短锁和数据库活动任务检查解决同供应商不同文件并发导入；两者约束不同。复用既有 Redisson 依赖，不把 Redis 锁跨请求线程与后台线程长期持有，不新增供应商排队任务或锁表。
